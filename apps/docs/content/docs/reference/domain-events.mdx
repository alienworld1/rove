title: "Domain Events"
description: "Distinguish persisted causal records from commands, observations, effects, and SSE."
---

Use this reference to interpret a session’s recorded history or build an integration that follows it. A request means work was queued; it does not mean funding, payment, or a physical pause has been confirmed. Browser update notifications are separate from these retained records.

The persisted event envelope is defined by `domainEvents` in `packages/persistence/src/schema.ts`. It includes ID, ordinal, type, schema version, Corridor/Lane/version/correlation/causation identifiers, reason, trace/occurred time, optional evidence/channel/transaction/CDR references, and a JSON payload. Ordinals order recorded notifications; trace time describes the controlled scenario independently of wall time.

These are bounded source-backed names, including dynamic Lane-state and payment-operation families. Payloads vary by emitter; there is no exhaustive discriminated universal payload union. The browser's safe Inspector and projection are narrower public read contracts than internal storage.

## What is not a domain event?

- HTTP commands express intent: `ObserveEvidence`, `CompleteLane`, `ReceiveCDR`, `CloseChannel`, clock/pause/recovery commands.
- Verified observations supply facts such as `EvidenceObserved`, `VoucherVerified`, `PaymentObserved`, and `ChannelClosed` to transitions.
- Outbox effects request external work, such as `payment.top_up_requested`, `payment.settlement_requested`, `payment.close_requested`, and `pause.requested`. Some share a name with a persisted event; their payload/transport is not interchangeable.
- SSE `projection_changed`, `lab_run_changed`, and `resync_required` are presentation notifications. They do not authorize payment or carry the whole domain payload.

## Safe interpretation

A requested/submitted payment event is not confirmation. Read the current operation and linked verified observation. A state event explains why the projection changed; it is not permission to bypass the current version/access gate. Example event names and schema structure below come only from versioned code, never a live private record.

See [API and SSE](/docs/reference/api), [reason meanings](/docs/reference/reason-codes), and [system overview](/docs/architecture/system-overview).

## Outbox and presentation name classification

`payment.open_requested` queues initial channel funding. `payment.voucher_requested`, `payment.top_up_requested`, and `payment.settlement_requested` are durable effect intents, not confirmation. `payment.close_requested` is both a retained intent event and a close effect. `pause.requested` also crosses the external control boundary.

The concrete lifecycle status names include `payment.open_submitted`, `payment.open_completed`, `payment.top_up_submitted`, `payment.top_up_completed`, `payment.settlement_submitted`, `payment.settlement_completed`, `payment.close_submitted`, `payment.close_completed`, `payment.voucher_completed`, and corresponding failed/pending statuses. They come from the dynamic operation/status emitter in `packages/persistence/src/index.ts`; completed work must be interpreted with its linked authoritative observation.

`payment.settlement_confirmed` is a retained read-model compatibility label, not a separate current transition emitter. `lane.closed` is the dynamic CLOSED state name, while `payment.channel_closed` carries canonical closure facts. Effect names and compatibility labels do not imply a universal payload schema.
